01 —

6つの層 — AI活用の進化階層

AI活用には明確な抽象度の階層がある。多くの人はLayer 1〜2で止まる。Layer 3で上位5%。Layer 4〜5を設計できる人が次世代のAIエンジニアだ。

✍️
Layer 1 — プロンプトエンジニアリング
LLMへの入力文を最適化する。指示の書き方、few-shot例の設計、Chain-of-Thoughtの誘導。スコープは単一プロンプト。"どう書くか"の技術。
L1PROMPT
指示の構造化（XML）Few-shot examplesChain-of-ThoughtRole promptingOutput format指定
🧠
Layer 2 — コンテキストエンジニアリング
コンテキストウィンドウ全体を設計・管理する。system prompt、会話履歴、RAG結果、ツール出力をどの順でどれだけ詰めるかの設計。"何を渡すか"の技術。
L2CONTEXT
System prompt設計RAG（検索拡張生成）Memory管理Tool output統合情報の優先順位付け
⚙️
Layer 3 — ハーネスエンジニアリング
LLMを実行・評価・制御するシステム基盤を構築する。エージェントループ、ツール呼び出し制御、エラーハンドリング、evals。"どう動かすか"の技術。Claude Code自体がこの層の代表例。
L3HARNESS
Agent loop設計Function callingEvals フレームワークエラーハンドリングロギング・モニタリング
🤖
Layer 4 — エージェント・オーケストレーション
複数のLLMが役割分担し、互いに会話しながら自律的にタスクを完遂する。Planner／Generator／Evaluatorのような分業と、それらの協調制御。"誰にやらせるか"の技術。
L4AGENTS
Multi-agent設計PGEループSupervisor / WorkerHand-off制御Agent mesh
🧬
Layer 5 — コンパウンドAIシステム
Berkeley BAIRが提唱した概念。「1つのLLMを賢くする」から「複数のLLM＋検索＋ツール＋評価器＋人間を組み合わせた1つのシステム」へ。モデル性能ではなくシステム設計が勝敗を決める段階。
L5COMPOUND
モデル選択の最適化パイプライン設計DSPyHuman-in-the-loopコスト×精度設計
♾️
Layer 6 — 自律AI / Self-improving Systems
AIが自分のハーネスを自分で改変する段階。新しいスキルを自分で書き、自分のメモリを整理し、失敗から学習する。まだ研究段階だが2026年以降の主戦場。"AIが自己進化する"フェーズ。
L6AUTONOMOUS
Self-improving agentsMeta-learningAI OSVoyager型学習Sakana AI系
⚡
構造認識： プロンプトはコンテキストの一部。コンテキストはハーネスの一部。ハーネスはエージェントの一部。エージェントはコンパウンドシステムの一部。外側を知らずに内側だけ学んでも天井は低い。
CORE CONCEPTS
概念一言定義判断基準よくある誤解
TokensLLMが処理する最小単位。文字≠トークン。コストとコンテキスト長はここで決まる文字数でカウントしようとする
Context Windowモデルが一度に"見える"範囲。ここに何を入れるかがすべて大きければ何でも入れていい
Temperature出力のランダム性。0=決定論的、1=創造的。タスクによって使い分ける高いほど賢い
System Promptモデルの役割・制約・出力形式を定義する。ここの設計でほぼ決まるユーザーメッセージより弱い
Function CallingLLMが外部ツールを呼び出す仕組み。エージェント化の基礎LLMが直接実行していると思う
RAG検索結果をコンテキストに注入して精度を上げる。ファインチューニング不要で知識を拡張できるファインチューニングと同義と思う
EvalsLLMの出力品質を定量的に評価する仕組み。"なんか良さそう"からの脱却人間が毎回チェックすれば十分
Agentic LoopLLMが自律的に行動→観察→次のアクションを繰り返す。複数ステップのタスク自動化の基礎単発の質問応答と同じ
Multi-agent複数のLLMが役割分担して協調する仕組み。単一エージェントの限界を超えるただLLMを並べれば協調すると思う
Orchestration複数エージェント・ツール・モデルの実行制御。LangGraph/CrewAI/AutoGen の核心単なる関数呼び出しの順序だと思う
Compound AI System複数モデル＋検索＋ツール＋人間を組み合わせた統合システム。モデルではなくシステム設計が差を生む「でかいモデル1個でいい」と思う
DSPyStanford発。プロンプトを"プログラム"として書くフレームワーク。プロンプトの手書き職人芸から脱却LangChainの上位互換だと思う
Self-improvingエージェントが自分でスキル・記憶・戦略を更新する。Voyager論文などの研究領域ファインチューニングと同じだと思う
02 —

コンパウンドAIシステム — 次の主戦場

2024年にBerkeley BAIRが発表した論文「The Shift from Models to Compound AI Systems」が業界の常識を変えた。もうモデル性能競争の時代じゃない。

なぜ「モデル1個」では勝てなくなったのか

GPT-4もClaude Opusも、単体では限界がある。2024年の最先端システムはほぼすべて「複数のAIコンポーネントを組み合わせたもの」だった。AlphaCode、AlphaGeometry、Devin、Perplexity、Claude Code — 全部コンパウンドAIシステム。

核心は3つ。①同じモデルでもシステム設計で性能は数倍変わる ②コストと精度のトレードオフを細かく制御できる ③人間・ツール・評価器を組み込める。これが単一モデルでは絶対にできない芸当だ。

03 —

学習ロードマップ

順序が命。各フェーズは「完璧になってから次へ」ではない。7割できたら進め。Phase 6〜7は現時点で実践している人が圧倒的に少ない領域。

01
APIの基礎と構造理解1〜2週間

「Claudeが動く仕組み」を知る。ブラックボックスをなくす最初のステップ。ここをスキップすると後でずっと詰まる。

Anthropic APIを叩くPythonで生のAPIレスポンスを見る。JSONの構造を把握する。
レスポンスの全フィールドを読むcontent, usage, stop_reason — 全部意味を調べる。
パラメータを一個ずつ変えるtemperature, max_tokens, system。変えると何が起きるか観察。
エラーを意図的に起こすrate limit、token超過、invalid requestの感覚を掴む。
02
プロンプト設計の体系化2〜3週間

「なんとなく書く」から「設計する」へ。公式ドキュメントを基礎にしつつ、自分のユースケースで繰り返し実験する。

公式Prompt Libraryを全部読むdocs.anthropic.com — なぜその構造なのかを考える。
XML構造でプロンプトを書く<task><context><output_format> の使い分けを習得。
Few-shotの設計例の質と数が出力品質に直結することを実験で確認。
失敗プロンプトを解剖する「うまくいかなかった」プロンプトの原因を6層で分類。
03
コンテキスト設計3〜4週間

何をコンテキストに入れるか、どの順で入れるか、何を切り捨てるか。情報の取捨選択こそが設計の本質。

System promptの設計原則役割、制約、出力形式、例外処理を分けて書く。
会話履歴の管理何件分の履歴を持つか。要約vs圧縮vs削除の判断。
RAGの基礎を実装検索→コンテキスト注入→回答生成の流れを手で動かす。
コンテキスト汚染を体験不要な情報を入れすぎて出力が劣化することを意図的に起こす。
04
ツール呼び出しとハーネス構築4〜6週間

LLMを「考えるだけ」から「行動できる」存在にする。ここから別次元になる。Claude Code自体のアーキテクチャを理解するのもこの段階。

Function callingを実装するtool_use でLLMが外部APIを呼び出す仕組みを手で理解。
シンプルなエージェントを作る「検索→読む→要約」の3ステップエージェント。
Anthropic "Building effective agents"を読む2024年12月公開の必読記事。パターン分類が秀逸。
エラーループに対処する無限ループに入ったとき何が原因か診断できるようになる。
05
Evals（評価）と品質管理継続的

出力品質を定量的に測れる人間が本当のAIエンジニア。最後のフェーズではなく、常に並行する作業。

テストケースを作る習慣プロンプトを変えるたびに同じ入力で出力を比較する。
LLM-as-judgeを実装別のLLMに出力を採点させる手法。人間レビューのスケール化。
失敗事例を分類するL1〜L6 どのカテゴリの失敗が多いかを把握する。
Anthropic Evalsを動かす公式ドキュメントのevals章を読んで実際に動かす。
06
マルチエージェント・オーケストレーション6〜8週間

複数のAIが協調するシステムを設計する。ここから「使う側」と「設計する側」が分かれる。てるさんの pricing-loop はまさにこの段階。

PGEループを自作するPlanner→Generator→Evaluatorを手で書く。役割分担の勘所を掴む。
LangGraphのチュートリアル状態機械としてエージェントを設計する感覚を養う。
CrewAI / AutoGenを触る役割ベースのマルチエージェント設計を体験する。
Claude Sub-agentsの活用Claude Code標準のサブエージェント機能を設計し分ける。
07
コンパウンドAIシステム設計継続的

モデル選択・ルーティング・評価器・人間レビューを統合した本番システムを設計する。ここができる人間は国内でまだ数百人しかいない。

BAIR論文を読む「The Shift from Models to Compound AI Systems」— 2024年の必読。
DSPyを触るStanford発。プロンプトを"プログラム"として書く新パラダイム。
モデルルーティング実装Haiku/Sonnet/Opusをタスク難易度で切り替える。コスト×精度の感覚。
Voyager論文を読むSelf-improving agentsの代表例。将来のLv6を覗く。
04 —

APIレスポンスの読み方

まず動かして、レスポンスを目で見る。これが最速の勉強法。

PYTHON — API基礎確認スクリプト
# pip3 install anthropic

import anthropic, json

client = anthropic.Anthropic(api_key="YOUR_API_KEY")

response = client.messages.create(
    model="claude-opus-4-6",
    max_tokens=1024,
    system="あなたは簡潔に答えるアシスタントです。",
    messages=[{"role": "user", "content": "東京の人口は？"}]
)

# ここを必ず読む — 全フィールドを確認する
print(json.dumps(response.model_dump(), indent=2, ensure_ascii=False))

実行すると以下のJSONが返る。各フィールドの意味を全部理解することがStep 1のゴール：

JSON — APIレスポンス構造（注釈付き）
{
  "id": "msg_01XxXx...",          // リクエストID（ログ・デバッグ用）
  "type": "message",
  "role": "assistant",
  "content": [                    // 実際の出力。配列形式に注意
    { "type": "text", "text": "東京の人口は約1,400万人..." }
  ],
  "model": "claude-opus-4-6",
  "stop_reason": "end_turn",      // ★ 必ずチェック（後述）
  "usage": {
    "input_tokens": 42,           // コスト計算と最適化に使う
    "output_tokens": 87          // input + output = 課金対象
  }
}
💡
stop_reasonを必ずチェックせよ。 "max_tokens"で止まっていたら出力が切れている。"tool_use"なら次のアクションが必要。ここを無視するとバグの温床になる。
COMPOUND SYSTEM — MODEL ROUTING 実装例
PYTHON — コスト最適化のためのモデルルーティング
# コンパウンドAIシステムの心臓部：タスクに応じてモデルを切り替える

def route_task(task_type: str, complexity: str) -> str:
    # 簡単な分類・抽出 → 最安モデル
    if task_type in ["classify", "extract"]:
        return "claude-haiku-4-5"

    # 通常の生成・要約 → 中位モデル
    if complexity == "medium":
        return "claude-sonnet-4-6"

    # 戦略判断・複雑推論 → 最上位モデル
    return "claude-opus-4-6"

# 使用例: PGEループ内で役割ごとに最適モデルを選ぶ
planner_model   = route_task("strategy", "high")     # Opus
generator_model = route_task("generate", "medium")   # Sonnet
evaluator_model = route_task("classify", "low")     # Haiku

# → これだけでコストは1/10、精度はほぼ維持できる

06 —

問題の診断フレームワーク

「うまくいかない」とき、原因がどの層にあるかを即座に特定できるか。これが「できてる」の本当の意味。

症状 → 原因層 マッピング

出力がおかしいとき、まずこの表で原因層を特定する

L1 — プロンプト問題
指示通りに動かない
フォーマットがバラバラ
トーンが期待と違う
関係ない情報を出してくる
日本語で答えてほしいのに英語
L2 — コンテキスト問題
長い会話で前の情報を忘れる
外部データを参照できない
回答がふわっとして具体性がない
複数ターンで一貫性がない
関係ない情報に引きずられる
L3 — ハーネス問題
たまに動いてたまに落ちる
エージェントがループする
ツール呼び出しが失敗する
レスポンスが突然切れる
本番で再現できないバグ
L4 — エージェント問題
役割分担が曖昧で仕事が重複する
エージェント間で情報が伝わらない
Plannerの計画が実行不可能
Evaluatorが常にOKを出してしまう
ループ回数が多すぎてコスト爆発
L5 — コンパウンド問題
安いモデルに重要判断を任せている
高いモデルを無駄に使っている
検証ステップが抜けていて精度不安定
人間レビューの挿入位置が間違っている
